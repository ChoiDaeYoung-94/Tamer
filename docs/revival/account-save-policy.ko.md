# 계정·저장 연속성 정책 (#96)

이 변경은 #95의 Unity 6000.0.81f1 복원·검증 도구에 의존한다. 계정 식별자 생성 규칙, 기존 자격 증명 방식, 상품 ID와 `GooglePlay`/`ProductNoAds` 계약은 유지한다. 운영 API 호출 없이 검증하며 통합 담당이 최종 병합한다.

## 로그인과 저장의 경계

| 상황 | 처리 |
| --- | --- |
| 기존 계정 로그인 | 인증된 계정의 서버 조회 성공 후 게임 진입. 서버 값으로 초기화하고 서버에 없는 필드는 배포된 기본값 사용 |
| 로컬·서버 진행도 충돌 | 최초 동기화 전에 기존 `PlayerData.json` 바이트를 `PlayerDataBackups`에 별도 보관. 로컬 전체 업로드·필드 수를 통한 신규 계정 추정 금지 |
| 최초 닉네임/캐릭터만 있는 계정 | 기본 진행도는 로컬에서 제공. 명시적인 닉네임·성별 저장과 이후 변경 키만 업로드 |
| 게임 중 변경 | `TryUpdateLocalData`가 원자적 로컬 저장에 성공하면 해당 키를 pending으로 기록. `UpdatePlayerData`는 그 스냅샷만 서버에 저장 |
| 업로드 중 추가 변경 | 저장 확인된 스냅샷과 현재 pending의 값·변경 순번이 모두 같은 키만 해제. 100→90→100처럼 값이 돌아와도 최신 변경은 보존 |
| 서버 오류·기한 초과 | 현재 요청과 대기 큐를 실패로 종료. pending은 보존하고 다음 저장 호출에서 재시도 |
| 손상된 숫자 데이터 | Gold 정수 범위와 능력치의 파싱/유한값을 저장 전에 검사. 임의로 0으로 바꾸지 않고 원본을 보존하며 동기화 실패 처리 |
| 알 수 없는 아군 몬스터 | 현재 몬스터 자료에 없는 토큰은 저장 전에 거절. 정상 중복과 빈 CSV 구분자는 기존 표현 유지 |
| 오프라인 로그인 | 로컬 데이터로 자동 진입하던 동작을 중단하고 재시도 표시. 미확인 계정에 저장을 허용하지 않음 |
| 게임 중 네트워크 단절 | 로컬 저장과 현재 플레이는 유지. 새 로그인 전까지 메모리 pending을 재전송 가능 |
| 재시작 후 미동기화 진행도 | 버전/서버 CAS 근거가 없으므로 자동 충돌 병합하지 않음. 서버를 사용하고 이전 로컬 파일은 복구 백업으로 보존 |

백업은 로컬 복구 자료이며 서버에 업로드하거나 공개 로그/이슈에 첨부하지 않는다. 자동 정리도 하지 않는다. 복구 시 현재 파일, 해당 백업, 계정 귀속을 함께 확인한 뒤 명시적으로 처리해야 한다. 단순히 골드의 큰 값을 고르는 방식은 구매/소비를 되돌리므로 사용하지 않는다.

## 계정 귀속과 재시도

- 로컬 JSON의 전용 `__TamerAccountOwner` 필드에 PlayFab 계정 귀속을 기록한다. 본문과 함께 한 파일로 원자적으로 교체하며 이 필드는 게임 딕셔너리/서버 patch에 포함하지 않는다. 기존 원본은 첫 적용 전에 백업한다.
- 기존 파일에 귀속 정보가 없으면, 기존 로그인 선택 정책을 통과한 첫 서버 조회 성공 시 귀속한다. 이후 다른 계정 ID는 자동 이전하지 않고 실패 처리한다.
- cached GPGS ID와 새로 인증된 ID가 다르면 기존 캐시를 교체하지 않는다. GPGS 실패 시 기존 캐시는 같은 계정의 로그인에만 사용한다.
- `android`, `custom`은 성공한 방식을 구분해 고정한다. 구버전 `device`와 CustomID가 공존하는 모호한 상태는 임의로 고르지 않고 복구를 요구한다. AndroidDeviceID 실패 후 CustomID로 새 계정을 만드는 fallback은 제거한다.
- 신규 생성은 플레이 기록·기존 귀속이 없는 최초 선택에만 허용한다. 최초 선택은 `*-pending`으로 저장해 timeout 재시도도 같은 식별자를 사용한다.
- 로컬 저장 로드에 실패한 상태는 이력이 불명확하므로 신규 계정 생성 권한으로 해석하지 않는다. 원본을 보존하고 복구가 필요하다.
- 로그인 시도 시작/실패/취소부터 쓰기를 중지한다. 요청별 인증 컨텍스트를 사용하고 승인된 로그인 결과만 활성 세션에 반영한다. 늦은 이전 결과가 새 세션을 바꾸지 못한다.
- 로그인·닉네임 저장·씬 진입은 중복 실행을 막는다. 캐릭터 선택은 성별 저장과 조회가 확인되어야 Main으로 이동하며 실패 시 같은 화면에서 다시 시도한다.

`LoginWithEmailAddress`는 계정 생성을 수행하지 않고 별도 등록 API를 사용한다. 오류가 계정 부재를 확정하지 못할 수 있으므로, 등록은 오류만으로 결정하지 않고 위 신규 선택 조건을 함께 확인한다. 기존 계정은 등록으로 전환하지 않는다. [공식 API 계약](https://learn.microsoft.com/en-us/rest/api/playfab/client/authentication/login-with-email-address?view=playfab-rest).

## 구매 권한 API (IAP 담당과 합의)

- `GooglePlay`는 쉼표로 구분된 토큰이며 No Ads는 정확한 `ProductNoAds` 토큰이다. `null`, 빈 토큰, 중복을 정리하되 알려지지 않은 다른 상품 토큰도 보존한다.
- 같은 계정의 로컬/서버 권한은 합집합으로 보존한다. 로그인 동기화는 기존 로컬 권한을 자동 취소하지 않는다. 이것은 영수증 검증이나 환불 판단을 대체하지 않는다.
- `bool TryGrantNoAds()`는 초기 서버 동기화 전에는 false. 이후 Player 오브젝트가 없어도 중복 없이 로컬 파일에 저장하고, 성공하면 해당 키의 서버 저장을 예약한 뒤 true를 반환한다.
- IAP는 true 후에만 pending 구매를 confirm한다. 로컬 저장 실패는 false/메모리 rollback이며 IAP는 pending을 유지한다. 서버 전송 실패는 이미 저장한 권한을 취소하지 않는다.
- `bool TryUpdateLocalData(string key, string value)`도 같은 로컬 저장 성공 계약을 제공한다. 기존 void 호출 API는 호환성을 위해 유지하며 저장 실패를 예외로 전달한다. 기존 IAP 코드가 저장 실패를 성공으로 오인하지 않게 하고, 출시 전 IAP 담당의 true 후 confirm 연동과 함께 검증한다.

## 검증 범위와 남은 한계

향후 사용자 데이터 쓰기는 `UserDataPermission.Private`를 지정한다. 자체 코드의 조회는 인증된 본인 계정만 사용하며 다른 플레이어 UserData 조회 의존성을 찾지 못했다. 기존 Public 키 중 이번에 쓰지 않은 키는 그대로 남고, 구버전 클라이언트는 다시 Public으로 쓸 수 있다. 운영 마이그레이션/구버전 대응은 #105에서 별도 추적하며 이 작업에서 서버 데이터를 일괄 변경하지 않는다. [공식 사용자 데이터 쓰기 계약](https://learn.microsoft.com/en-us/rest/api/playfab/client/player-data-management/update-user-data?view=playfab-rest).

가짜 네트워크와 시계로 요청 스냅샷·10개 키 분할·재시도·늦은/중복 콜백·계정 변경을 검사한다. 임시 파일로 서버 진행도 적용, 원본 백업, 단일 파일 귀속, 권한 저장 실패를 검사한다. 실제 Editor 결과와 커밋은 `account-save-validation.json`에 기록한다.

현재 변경은 다중 기기 동시 저장에 대한 서버 트랜잭션/CAS를 추가하지 않는다. 여러 배치 중 일부만 성공한 뒤 최종 실패할 수 있고, 이미 서버가 수락한 요청을 취소로 되돌릴 수 없다. 멱등 키 할당을 재시도하며 원격 동시 쓰기의 원자성을 주장하지 않는다.

도감·장비의 별도 PlayerPrefs(`AllyMonsters`, `LocalItem`, `playerEquippedItems`)는 이번 변경에서 이동/초기화하지 않는다. 이 자료의 계정별 분리는 별도 마이그레이션 증거가 필요하다. 기존 인증 방식의 보안 현대화, 로컬 백업 선택 UI, 버전 있는 오프라인 병합, 기기별 로그인/구매 복원과 실제 스토어 검증은 후속 범위다.

되돌릴 때도 현재 저장 파일과 백업을 먼저 보존한다. 새 귀속 메타데이터가 있는 파일을 구버전의 전체-dict 동기화 코드에 그대로 넣지 않는다. 구버전으로 실행하기 전 메타데이터를 제외한 복사본으로 별도 검증하고 서버 변경은 자동 수행하지 않는다.
