### 2026-09-23 별도 보관 없음 원칙 — 운영 검증 전

운영 원칙은 Monster Tamer 계정 삭제 처리 후 해당 게임 계정과 진행 데이터의 별도 보관용 사본을 만들지 않는 것이다. 접수·본인 확인에 필요한 이메일 원문과 확인 자료는 처리 종료 후 삭제하고 별도로 보관하지 않는다. 이 원칙은 현재 PlayFab의 삭제 범위, 백업·로그·PlayStream·메일 서비스·처리자 잔존 자료가 실제로 정리됐다는 증거가 아니다. 운영 타이틀 연결과 공급자별 처리 결과를 확인한 뒤 공개 안내의 삭제 항목·예외·처리 기간을 확정한다.

Google 계정과 Google Play 구매 기록은 이 게임의 계정 삭제 대상이 아니며 구매 복원 경로는 유지한다. PR #235의 기존 `.deletion-entitlement-*` 정리는 소유자와 형식이 확인되는 사본에만 적용되며 실기기 검증과 삭제 후 새 계정의 구매 복원 확인은 남아 있다. 타인·소유 불명 사본과 접근할 수 없는 기기의 자료는 임의로 삭제하거나 삭제 완료라고 신고하지 않는다. 자체 보관 기간을 임의로 만들지 않되 실제로 남는 제공자·접수 기록이 확인되면 대상·이유·기간을 구분해 안내한다.

## 계정 삭제 경로의 구체적 누락과 구현 계약

`Login`은 `RegisterPlayFabUser` 및 `CreateAccount` 조건부 로그인으로 계정을 만든다.
`ServerManager.DeleteData`의 UserData 키 제거는 계정 삭제가 아니다. 앱 설정의 삭제 진입점,
본인 확인 서버, 접수 상태, 완료 처리, 삭제용 웹 페이지는 이번 소스에서 확인되지 않았다.
기존 README 연락처는 일반 개인정보 문의 주소다. 운영자가 실제 접수·본인 확인·처리를 맡는다는
확인 없이 그 주소를 작동하는 계정 삭제 서비스로 바꾸어 약속하지 않는다.

[Google 계정 삭제 요구사항](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en)은
앱 내 진입 경로와 앱을 재설치하지 않아도 요청할 수 있는 웹 경로를 요구하며, 앱 내 링크를
웹 삭제 리소스로 연결하는 방식도 설명한다. 따라서 다음 구현은 실제 접수 서비스와 함께 제공한다.

| 단계 | 준비할 구현과 완료 조건 |
| --- | --- |
| 접수 | 설정의 “계정 및 데이터 삭제 요청” → 운영 중인 전용 HTTPS 페이지. 앱/개발자 이름, 삭제 대상·남는 대상·처리 예상 기간·연락 방법 표시. 기간은 담당자가 확정 |
| 본인 확인 | 신뢰할 수 있는 로그인/서버 세션으로 대상 계정을 확정. 공개 닉네임·PlayFabId만으로 삭제 승인 금지. 앱 접근 불가 사용자용 지원 절차 별도 마련. 비밀번호·전체 영수증을 공개 이슈에 받지 않음 |
| 영향 확인 | 진행도·프로필·로컬 백업·계정 연결 및 No Ads 복원 영향 안내 후 이용자의 실제 삭제 의사 확인. 요청 중/취소 가능 시점/완료 상태 구별 |
| 서버 처리 | 제목(title) 범위와 master 계정의 다른 게임 영향부터 확인. 서버 비밀을 보관한 운영 서비스만 삭제 API 수행. 작업 접수와 완료를 구별하고 재시도 중복 방지 |
| 연관 데이터 | UserData뿐 아니라 프로필·연결 계정·이벤트·사용 중인 Entity 데이터·운영 로그/백업·처리자 데이터를 조사. 정당한 보관 예외가 실제 존재할 때만 대상·근거·기간 명시 |
| 단말 처리 | 인증된 완료 상태 후 저장 큐/자동 저장·로그인 세션을 중단하고 해당 계정의 PlayerData.json·PlayerDataBackups·로그인 PlayerPrefs 처리. 임의 전체 PlayerPrefs 삭제로 다른 설정을 지우지 않음. 다른 기기는 완료 상태를 확인하기 전 자동 재생성/재업로드하지 않도록 설계 |
| 구매 권한 | 스토어 구매 기록과 게임 계정 삭제를 구별. 기존 No Ads를 일반 로그인/업데이트에서 회수하지 않음. 삭제 후 복원/재가입 정책은 운영자가 확정하고 안내·시험 |

[PlayFab 삭제 안내](https://learn.microsoft.com/en-us/xbox/playfab/data-analytics/privacy-compliance/gdpr-deleting-player-data)는
Master 계정 삭제, 이벤트 삭제, 개별 데이터 삭제를 구별한다. Master 삭제는 다른 title에도 영향을
줄 수 있고 JobReceiptId는 접수 증거이며 완료 증거와 다르다. 이번에는 삭제 API를 호출하지 않았다.

웹 페이지에 붙일 문구 구조는 “Monster Tamer 계정 및 데이터 삭제 요청 / 요청 방법 / 본인 확인 /
삭제되는 데이터 / 보관되는 데이터와 근거·기간 / 구매 복원 영향 / 처리 일정 / 문의”다.
미확정 운영 사실을 빈칸이나 임의 값으로 공개하지 않는다. 개인정보처리방침은 이 접수 페이지와
별도로 실제 수집·목적·수신자·보관·아동 처리·보안·운영 주체·시행일을 포함해 개정해야 한다.

## 영수증 검증 경계

`IAPManager.IsSupportedPaidOrder`는 주문 상태, 영수증 문자열 존재, Pending 거래 ID,
단일 No Ads 상품·수량·NonConsumable 유형을 검사한다. `NoAdsPurchaseFulfillment`는
로컬 영구 지급 성공 후 confirm한다. **이 검사는 서버의 영수증 진위 검증이 아니다.**
앱 코드에서 스토어 영수증을 자체 서버/PlayFab 검증 API에 전달하는 경로는 발견하지 못했다.
따라서 현재 PlayFab에 저장하는 No Ads 문자열을 서버 검증된 구매 증거로 설명할 수 없다.
Private UserData는 타인에게 읽히는 범위를 줄이지만 본인 클라이언트의 위조 쓰기까지 막지 않는다.

[Unity IAP 5 영수증 검증 안내](https://docs.unity.com/en-us/iap/receipt-validation)는
원격 검증 서비스가 기본 제공되지 않으며 서버 검증 구현을 권장한다고 설명한다.
후속 구현은 인증된 계정에 영수증을 묶고 상품·앱·스토어·구매 상태를 서버에서 검증하며,
거래 재사용/계정 간 중복 지급을 방지하는 기록과 내구성 있는 지급 후 confirm 순서를 갖춰야 한다.
네트워크 실패는 pending을 유지하고, 영수증 원문·토큰을 공개 로그/분석 이벤트로 보내지 않는다.
이때 새로 생기는 서버 수집 데이터·목적·보관·삭제 범위도 신고에 추가 검토한다.
기존 No Ads 계정을 영수증 부재만으로 무효화하지 말고 별도 호환 정책과 합성 테스트를 먼저 마련한다.

이번 PR은 삭제 서비스나 서버 검증을 구현했다고 주장하지 않는다. 해당 기능은 운영 주체·서버
경계·삭제 범위가 있어야 안전하게 완성할 수 있다. 검증 가능한 로컬 준비물은
[Public 이행 도구와 비교 계약](userdata-private-migration.ko.md)이며 운영 상태는 바꾸지 않는다.
