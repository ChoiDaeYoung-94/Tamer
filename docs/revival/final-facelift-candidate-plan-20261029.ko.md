## 실행 순서와 완료 기준

1. 사용자에게 현재 아이콘·주요 화면과 검증 한계를 보여드리고 추가 UI 의견을 반영합니다. 새 작업 범위가 정해지면 해당 부분만 확인합니다.
2. 위 의존성에 맞는 정상 Play 시험 제공 경로를 구체화합니다. 내부 트랙 재개/제공은 별도 승인 범위이며 지금은 변경하지 않습니다. 새 최종 후보를 제공할지 보존27로 필요한 계정 확인을 먼저 할지는 검토 결과와 실제 제공 조건에 따라 정합니다.
3. 운영 기능에서는 기존 계정 로그인·서버 진행/소유권·필요 저장 연속성·기존 No Ads/구매 복원·동의/광고 차단과 권한 있는 삭제 접수 범위를 최소한으로 연결합니다. 실제 인증/휴대폰/비밀 입력은 직접 조작하며 새 결제·환불·기존 데이터 삭제·계정 이전은 추가하지 않습니다.
4. 실제 최종 checkout/HEAD·origin/main·미커밋 변경과 전체 Console 번호를 다시 확인합니다. 현재 최신 목록에는27이 있지만 전체 번호 확인을 새 생성 직전에 다시 해야 합니다. 다음 코드 값은 아직 미확정입니다.
5. 새 소스의 plan/source-review·native metadata/binding·보호 파일 snapshot을 다시 준비합니다. 과거27용 source-review/manifest/receipt/collector 핸들을 새 후보에 재사용하지 않습니다. 기존 키·alias·계정·No Ads·Library와 비공개 복원 원본을 보존합니다.
6. canonical QuadDIntro→Login 순서·공통 패키지 pin·UI GUID/이벤트 보존과 운영 build-only 기호 제외를 확인합니다. 로그인/광고·PGS metadata 주입이 원래 보호 계약을 만족해야 하며 시험 앱 ID/debug signing·메모리 서버/관찰기가 운영 파일에 섞이지 않아야 합니다.
7. 필요한 키 직접 입력 이후 새 후보를1회 생성하고 실제 APK/AAB의 package/version/SDK/ABI·서명·manifest/resource payload·하네스 제외·관련 native 배치를 확인합니다. 새 실행과 관계없는 과거 전체 회귀를 반복하지 않고 정확한 source/도구/APK SHA·실패/미검증과 원본 복구를 기록합니다.
8. 원래 설정/비공개 staging·보호 파일 복구와 소유 프로세스 종료를 확인한 뒤 필요한 업로드/정상 Play 제공물 확인으로 연결합니다. 사용자 최종 검토와 별도 승인 전 실제 심사 전송·프로덕션 배포·트랙 재개를 하지 않습니다.
