# 개인정보 후속 실행 준비와 운영 결정 (#105)

현재 상태 대조: 2026-09-12 KST, 기준 main `40b23cc954a2ea9a9a36eca9a58c5ad79ca246da`.
최초 준비안의 이력은 검증 JSON에 보존한다. 이후 삭제 core·앱 UI·합성 HTTP 계약은 구현·검증됐으며,
사용자가 별도 승인한 기존 76개 타이틀 계정 삭제는 최종 일반 목록·세그먼트 0명까지 확인했다.
이는 운영 삭제 접수 서비스의 배포나 모든 부속 데이터의 물리적 소거 완료를 뜻하지 않는다.
기존 README 정책과 Console 정책 URL은 보존 확인됐으며, 이번 문서 정정에서는 외부 조회·변경을 하지 않았다.
[Data Safety 답안 후보](data-safety-draft.ko.md), [기술 감사](privacy-data-safety-audit.ko.md),
[Public 이행 계약](userdata-private-migration.ko.md)을 대체하지 않고 실행 순서와 결정 책임을 보완한다.

## 현재 준비 상태

| 작업 | 준비된 근거 | 다음 완료 조건 |
| --- | --- | --- |
| 수집 신고 | ID·닉네임·진행도·구매 권한의 소스 경로와 SDK 후보 분류 | 제공 중인 모든 버전/지역과 다음 후보를 대조하고 처리자·목적·선택 여부 확정 |
| 삭제 | core·UI 합성 흐름 및 실제 C#→Python loopback HTTP 계약 검증; 별도 승인한 기존 76개 타이틀 계정의 최종 UI 잔여 0명 | 실제 접수 창구·운영 재인증/공급자 adapter·배포, 단말 정리/복귀와 다기기 통제의 운영 검증 |
| 보관 | 아래 대상별 조사 대장 | 운영 주체가 목적·기간·삭제 방법·예외 근거를 승인하고 공급자 근거 확보 |
| Private 이행 | 합성 입력 기반 집계·pre/postflight 도구; 기존 76개 타이틀 계정은 삭제 후 UI 잔여 0명 | 삭제된 76개에 대한 이행 작업은 없음. 실제 대상 재등장 시에만 모집단·Public 키·쓰기 통제를 재평가 |

완료 근거는 [core](account-deletion-test-flow.ko.md), [UI](deletion-ui.ko.md),
[HTTP 계약](deletion-loopback-http.ko.md), [기존 계정 삭제](title-player-deletion-execution.ko.md),
[정책 보존](privacy-policy-continuity.ko.md)을 구분한다. HTTP 검증은 실제 C# 소스를 연결한 .NET 실행이며
Unity UI의 HTTP 클릭이나 Android/IL2CPP 검증을 뜻하지 않는다. 운영 gateway는 기본 비활성이다.

PR #121의 Data.Shutdown/Server.Dispose는 현재 프로세스의 저장·재시도·늦은 응답을 멈춘다.
삭제 접수 상태를 서버에 보존하거나 다른 기기의 재로그인/재업로드를 막는 기능은 아니다.
일반 로그인·업데이트에서 기존 저장·No Ads·백업을 지우지 않는 계약은 계속 유지한다.

## 삭제 범위와 완료 상태 설계

[Google 요구사항](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en)에 맞춰
앱 설정의 삭제 진입점과 재설치 없이 사용할 웹 접수 경로를 함께 준비한다. 페이지에는 앱/개발자명,
삭제·보관 범위, 실제 처리 일정, 문의 방법을 표시한다. 현재 README 문의 주소의 운영 여부는 미확정이다.

| 수단 | 범위와 한계 | 이 프로젝트의 판단 |
| --- | --- | --- |
| Client UserData 키 제거 | 특정 키 제거; 계정·인증·이벤트 삭제 아님 | 계정 삭제 구현으로 재사용하지 않음 |
| Admin DeletePlayer | title 계정 데이터 삭제를 예약하지만 PlayStream 이력과 publisher 계정/연결 등은 남김 | 단일 title 요구라도 이것만으로 전체 삭제 완료라고 알리지 않음 |
| Admin DeleteMasterPlayerAccount | 모든 관련 title의 master 데이터 삭제를 예약. JobReceiptId 반환과 완료 통지는 별개 | 다른 게임 영향 확인과 별도 범위 승인 없이 기본 선택하지 않음 |

API 범위·비동기 동작의 근거는 [DeletePlayer](https://learn.microsoft.com/en-us/rest/api/playfab/admin/account-management/delete-player?view=playfab-rest)와
[DeleteMasterPlayerAccount](https://learn.microsoft.com/en-us/rest/api/playfab/admin/account-management/delete-master-player-account?view=playfab-rest)다.
master 작업 전 GetPlayedTitleList로 영향 범위를 확인하도록 공식 문서가 안내한다.
Console의 AllowServerToDeleteUsers 꺼짐은 [관측 당시 상태](playfab-console-observation.ko.md)이며
Admin 경로의 불가능 또는 성공을 증명하지 않는다. 설정 변경과 API 호출은 이번 범위 밖이다.

다음 상태는 운영 설계 계약이다. core·UI·합성 서버 구현은 완료됐지만 운영 중인 삭제 서비스는 아니다.

| 상태 | 진입 조건·처리 | 다음 상태를 인정하는 증거 |
| --- | --- | --- |
| 접수/본인 확인 대기 | 서버가 생성한 요청 번호. 공개 닉네임/계정 ID만으로 대상 확정 금지 | 유효한 인증 세션 또는 담당자가 승인한 복구 본인 확인 |
| 범위·의사 확인 | title/master 영향, 구매 복원, 예외 보관 안내. 현재 로그인 계정과 요청 대상 일치 확인 | 동일 대상에 대한 이용자 확인과 운영 처리 범위 기록 |
| 실행 대기 | 서버에서 해당 대상의 새 쓰기/로그인 재생성 통제. 아직 작업을 제출하지 않았다면 취소 처리 가능 | 통제 유효성·작업 대상·중복 방지 키의 내구성 기록 |
| 삭제 진행 | 서버 비밀을 가진 제한된 서비스만 제출. 네트워크 응답 유실은 성공/실패로 추정하지 않음 | 작업 접수/공급자 상태를 대조; 이전 요청을 무조건 재실행하지 않음 |
| 부분 완료/확인 필요 | PlayFab, 자체 저장, 로그/백업, 처리자별 상태를 분리 | 각 대상 완료 또는 승인된 예외 보관 증거. 실패 시 완료 안내 금지 |
| 완료 | 접수 응답만으로 전환 금지. master라면 공식 완료 통지와 범위 대조 | 이용자 통지, 단말의 해당 계정 정리, 제한된 감사 기록과 그 만료 시점 |

취소 가능 시점은 서버 작업 제출 전으로 제안한다. 제출 후 복원이 가능하다고 약속하지 않는다.
재가입 허용 시점·구매 복원 정책은 아래 D4에서 결정한다. 현재 로그인은 자동 생성 경로가 있으므로
삭제 완료 후 같은 식별자의 신규 가입을 기존 삭제 취소로 취급하지 않는 흐름이 필요하다.
다른 기기나 구버전의 재업로드를 실제로 막는 서버 통제 없이 클라이언트 표시만 추가하지 않는다.

## 저장·보관 조사 대장

기간 숫자는 아직 정하지 않았다. 각 행의 운영 담당자는 목적, 보관 기산점, 활성 데이터/백업 각각의
최대 기간, 삭제·만료 방법, 접근자, 예외 근거와 종료 조건을 채워야 한다. 무기한을 기본값으로 두지 않는다.

| 대상 | 확인된 근거/범위 | 삭제·보관 결정을 위한 추가 확인 |
| --- | --- | --- |
| PlayFab 계정/프로필/UserData | ID, 닉네임, 진행도, GooglePlay 권한; 향후 쓰기는 Private | title/master 연결, 사용 중인 다른 Entity·inventory·publisher 데이터, 실제 백업/삭제 완료 범위 |
| PlayFab 이벤트·IP·장치/집중 시간 | Console에서 수집 관련 설정 켜짐, 실제 기간 미확인 | PlayStream/Telemetry별 목적·보관·내보내기 사본·공급자 삭제 확인 방법 |
| PlayerData.json 및 임시 저장 | DataManager의 persistentDataPath 파일과 저장 중 임시 파일 | 해당 계정 귀속 확인 후 처리. 다른 사용자 파일과 진행 중 저장을 삭제하지 않도록 격리 |
| PlayerDataBackups | 계정 전환 복구용 GUID 파일명; 자동 만료 없음 | 파일명으로 계정 추정 금지. 내용의 귀속으로 분류하고 미확인 레거시 사본은 별도 처리 결정 |
| 로그인 PlayerPrefs | AD_LastGpgsId, AD_CustomId, AD_LoginMode | 완료 대상과 현재 세션 일치 검사. DeleteAll 금지; 음량 등 무관 설정 유지 |
| 구매·복원/검증 기록 | 기준 소스의 상점 주문·No Ads 지급에 더해, 후속 PR #120/main `3cfc0ff`에서 미배포 테스트 전용 SQLite grants의 `token_hash`, `account`, `product`, `package` 스키마를 확인 | 이 검증 기록도 활성화 전 삭제·보관 대상에 포함. 계정·거래 연결 해시는 익명 데이터가 아니며 스토어 구매 기록과 별도. 기간·삭제 방법은 D3/D4에서 확정 |
| Google/Unity/광고 처리자 | GPGS, IAP 이벤트, 광고 관련 기술 감사 | 계약상 역할, 실제 활성 SDK, 자체 목적/대행 처리, 이용자 요청 전달·완료 방법과 근거 |
| 지원 요청/운영 로그/백업 | 실제 접수·로깅 체계 미확정 | 본인 확인 자료 최소화, 공개 이슈 접수 금지, 로그 필드와 사본 만료를 함께 설계 |
| 삭제 상태·감사 기록 | 재업로드 방지와 요청 중복 방지에 필요한 설계 후보 | 계정 연결 해시는 익명으로 간주하지 않음. 최소 필드·목적·기간 및 해제 시점 승인 |

삭제 API가 Google Play 구매 기록이나 외부 공급자 사본, 오프라인 기기의 파일을 동시에 제거한다고
표시하지 않는다. 처리자 삭제 요청과 예외 보관 고지는 [Google 계정 삭제 안내](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en)와 대조한다.
지역별 법정 기간을 추정해 채우지 않고 운영 주체의 적용 범위 검토를 남긴다.

## Public→Private 실행 검토 묶음

아래 절차는 실제 대상이 다시 확인될 때 재평가할 조건부 계약이다. 삭제된 기존 76개를 대상으로
내보내기·canary·이행을 실행할 잔여 작업으로 두지 않는다. 대상 확인을 위해 새 로그인·계정 재생성·
추가 삭제 또는 조회 반복을 하지 않는다. 최종 0명 관찰은 과거 권한 이행을 수행했다는 뜻도 아니다.

기존 도구에는 운영 쓰기나 요청 payload 출력이 없다. 아래 항목이 충족된 뒤에도 실제 실행은 별도 승인한다.

1. **대상 확인:** title·모집단·known/unknown 키 집계, 모든 공개 조회 소비자, 서버·구버전 쓰기 주체 목록.
   UserData 전체 응답임을 운영자가 증명하며, 공개 조회 결과나 생략된 응답을 전체로 포장하지 않는다.
2. **쓰기 배제 시험:** 현재 앱·구버전·CloudScript·운영 도구의 경합을 합성 환경에서 차단/직렬화한다.
   DataVersion preflight는 변경 탐지이며 CAS가 아니다. 차단을 입증하지 못하면 실행 보류한다.
3. **합성 canary:** Gold의 앞자리 0, CSV 순서, ProductNoAds와 과거 토큰, 빈 문자열을 그대로 보존.
   unknown Public 키는 자동 변경하지 않는다. 계정 간 공개 조회 비노출은 승인된 별도 합성 계정에서 확인한다.
4. **승인 대상 묶음:** 정확한 실행기 소스/리뷰, 대상 수, 변경 키, 쓰기 통제, 개인 백업 보관 기준,
   실행 창, 중지 기준, 담당자, 재시도·응답 유실 처리와 검증 결과를 묶어 운영자가 검토한다.
5. **실행/검증 계약:** 쓰기를 막은 상태에서 최신 값을 읽고 preflight → 권한만 변경 → 전체 재조회로
   postflight와 after audit. 오류·값/키 차이·예상치 못한 권한 변화·통제 해제 시 다음 대상을 중지한다.
6. **복구:** 오래된 값 재전송 또는 Public 되돌리기 자동 rollback 금지. 현재 값을 다시 조회하여 원인을
   판별하고 값 보존 복구안을 별도 검토한다. 재개 후 구버전 재공개 여부의 확인 주체·주기를 정한다.

## root가 운영자에게 확인할 결정 목록

[기존 공개 정책 대조](privacy-policy-continuity.ko.md)에서 운영자·일반 문의·기존 시행일과 현재 Console 정책 URL을 확인했다. 이 기재 사항은 다시 묻지 않으며, 일반 문의를 운영 삭제 서비스로 확대하지 않는다. D2–D8의 미정 사항은 원문에 없다.

| ID | 필요한 결정 | 결정 후 만들거나 승인할 결과 |
| --- | --- | --- |
| D1 | 기존 운영자·일반 문의·정책 URL은 재사용. 미정인 실제 삭제 접수 경로·처리 책임과 실행 방식 | 실제 접수 흐름과 앱 링크. 정책 개정이 필요할 때 확인된 처리 사실과 개정일 반영 |
| D2 | 기존 76개 정리는 title 한정으로 승인·실행 완료. 향후 이용자 삭제 서비스의 title/master 범위와 다른 title 영향은 미정 | 향후 본인 확인/영향 안내와 이벤트/연관 저장 처리 범위 |
| D3 | 대상별 보관 목적·기간·예외와 처리자 확인 담당 | 위 보관 대장, 사용자 고지, 로그/백업 만료 구현 |
| D4 | 삭제 후 재가입·No Ads 구매 복원·미확인 레거시 백업 처리 | 계정 생성/복원 UX와 다기기·구버전 합성 시험 기준 |
| D5 | 현재 제공 트랙/버전·지역, SDK 실제 활성 범위와 처리자 역할 | 최종 Data Safety 유형/필수·선택/공유·전송 암호화 답안 |
| D6 | 실제 대상 재등장 시 Public 키·공개 조회 사용처·구버전 쓰기 차단 방식 재평가 | 조건부 canary/실행기 검토; 삭제된 76개에 대한 이행 작업 없음 |
| D7 | 합성 staging title/계정 사용 범위와 서버 실행 환경 | 인증·삭제/복원·이행 end-to-end 검증. 실제 회원 계정 사용 없음 |
| D8 | 게시·Console 수정·운영 이행 각각의 승인 주체 | 최종 문구/URL/대상/변경내용을 확인한 별도 실행 승인 |

이 결정 요청은 운영 변경 승인 요청과 다르다. 먼저 운영 사실을 확정하고 기능·문구·검증 자료를
완성한 뒤 해당 결과를 대상으로 게시/설정/운영 실행을 승인받는다. 미구현 삭제 지원을 신고하지 않는다.
[Data Safety 공식 안내](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en)는 SDK를 포함한
실제 처리에 대한 정확한 신고 책임을 개발자에게 둔다. 수집 있음 근거와 공유 예외 판단을 분리한다.

## 오프라인 확인과 남은 검증

`python -m unittest discover -s tools/revival -p "test_audit_userdata_privacy.py" -v`로 기존 비교 도구를
합성 입력에서 재검증한다. 소스/도구 해시와 결과는 [검증 기록](privacy-readiness-validation.json)에 둔다.
단위 테스트는 운영 스냅샷의 완전성, 쓰기 잠금, 공급자 삭제 완료, 정책 준수를 증명하지 않는다.
삭제 상태 표의 운영 조건과 이미 완료된 합성 구현 검증을 구분한다. 이 문서 정정에서는 기존 검증 기록을
대조했으며 테스트를 새로 실행하지 않았다. Unity/Android 작업은 이 문서 변경에 필요하지 않다.
